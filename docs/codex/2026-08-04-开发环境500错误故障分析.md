# 开发环境 500 错误故障分析

## 背景与现象

2026-08-04，开发环境用户端 `http://127.0.0.1:18775/` 在登录后打开页面时只显示 `Internal Server Error`。Docker 中 PostgreSQL、API、用户端和管理端容器均保持运行，因此需要区分“服务未启动”和“页面初始化业务异常”。

## 已验证事实与证据

1. PostgreSQL 容器健康，API `/health` 返回 200；用户端和管理端端口也可访问。
2. 用户端异常堆栈发生在页面初始化期间：
   - `desktop.py` 构建选题中心；
   - `TopicSourceService.__init__()` 调用 `ensure_defaults()`；
   - `ensure_defaults()` 尝试写入默认选题来源；
   - `Database._assert_write_owner()` 抛出“该配置不属于当前登录账号”。
3. 当前 PostgreSQL 中六条默认选题来源使用固定 ID，并全部归属默认管理员 `lanxue`：
   - `internal-followed-accounts`
   - `internal-manual-topics`
   - `news-bing-management`
   - `hot-weibo`
   - `hot-baidu`
   - `rss-d99de66c0b1a`
4. 使用隔离的临时 SQLite 数据库复现：先由管理员初始化默认来源，再由第二个用户初始化相同来源，稳定触发同一所有权错误。

## 根本原因

`topic_sources` 已经改为按 `owner_user_id` 隔离，但表的主键仍只有全局 `id`。默认来源的 ID 又是代码固定值。

第二个用户读取固定 ID 时，带有用户作用域的查询看不到 `lanxue` 的记录，因此业务层判断“来源不存在”；随后它使用相同固定 ID 插入自己的来源。数据库中该 ID 已存在，写入前的所有权检查发现记录属于 `lanxue`，于是拒绝越权写入。该异常没有在页面初始化层转换为可恢复状态，最终表现为 HTTP 500。

简化链路如下：

```text
用户 B 登录
  -> 按用户 B 查询 hot-weibo：查不到
  -> 认为默认来源尚未创建
  -> 尝试插入固定 ID hot-weibo
  -> 数据库发现该 ID 已属于 lanxue
  -> 所有权校验拒绝写入
  -> 页面初始化中断并返回 500
```

## 次生错误

日志中的 `The parent slot of Timer ... has been deleted` 是页面创建失败后，已注册的 NiceGUI 定时器仍尝试访问已销毁页面容器产生的次生异常。它不是最初的故障原因；先解决选题来源主键/归属冲突后，再确认是否仍需单独清理定时器生命周期。

## 影响范围

- `lanxue` 本人通常可以正常读取既有默认来源。
- 新注册用户或其他用户首次打开包含选题中心的主页面时可能直接 500。
- 不影响 PostgreSQL、API 健康检查和管理后台启动。
- 数据库所有权校验本身行为正确，不应通过放宽或删除校验解决。

## 已实施修复

1. `topic_sources` 新增语义字段 `source_key`，并建立 `(owner_user_id, source_key)` 唯一约束。
2. `hot-weibo`、`hot-baidu` 等固定值只作为租户内的语义键；实际数据库行 ID 使用“用户＋来源键”生成的稳定 ID。
3. 默认来源改为在已认证用户作用域内惰性、幂等初始化，不再在共享 API 服务构造阶段写入管理员数据。
4. 选题搜索线程显式传播当前用户作用域，避免线程池丢失 `ContextVar` 后写成平台全局数据。
5. “手动选题”按 `source_key` 解析真实行 ID；列表筛选同时兼容旧物理 ID 和语义键。
6. 相邻的默认关注公众号导入也改为按用户生成 ID，避免同名默认公众号在第二个用户下发生同类冲突。
7. PostgreSQL 并发写入使用 `(owner_user_id, source_key)` 冲突目标，消除并发首次初始化的唯一键竞争。

## 验收标准

1. 管理员和两个普通用户依次或并发首次登录，均可打开工作台和选题库。
2. 三个用户各自能看到默认来源，修改启停状态互不影响。
3. 用户 B 无法读取或修改用户 A 的自定义来源。
4. 历史 `lanxue` 选题来源内容和状态迁移前后保持不变。
5. 页面初始化不再出现“该配置不属于当前登录账号”或 `Internal Server Error`。
6. 完整自动化测试和 PostgreSQL 双用户集成测试通过。

## 验证结果

- 相关自动化回归：48 项通过。
- 真实临时 PostgreSQL 并发验证：2 个用户分别发起 12 个并发初始化请求；每个用户最终恰好保留 6 个默认来源，两组物理 ID 完全不重叠。
- 历史 PostgreSQL 数据迁移后，`(owner_user_id, source_key)` 重复数为 0。
- 用户所有权校验仍保留，修复没有通过放宽授权来绕开故障。

最终结论：导致登录后首页 `Internal Server Error` 的主因已修复。重新构建并启动用户端、API 和管理端后，三个入口均返回 200；管理员与临时普通用户的认证选题来源请求均成功。重启后的日志中没有再出现所有权冲突、`Internal Server Error`、deleted client 或 Python traceback，因此 NiceGUI 次生错误也随主故障消失。
