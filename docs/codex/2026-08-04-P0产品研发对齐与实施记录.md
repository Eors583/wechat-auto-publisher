## 一、实际收到并确认的三项 P0

1. **统一批次状态口径**：文章全部确认、尚未写入草稿时，批次必须显示“待写入草稿”，收件箱、批次卡、步骤条和外部通知不得继续显示“待审核”。

## 三、P0-1：统一批次状态口径

### 研发判断

旧逻辑只依据文章 `job.status` 推导批次状态。文章确认后，业务状态仍为 `ready_for_review`，只有 `review_status` 变成 `confirmed`，因此批次被错误投影为“待审核”。

### 开发任务与实现证据

1. `app/services/batch_contracts.py`
   - `progress` 新增 `ready_for_draft` 计数。
   - `effective_batch_status()` 同时判断文章状态与审核状态。
2. `app/db.py`
   - 收件箱新增 `ready_for_draft` 桶，查询条件为 `j.status='ready_for_review' AND review_status='confirmed'`。
3. `app/services/batches.py`、`app/services/batch_progress.py`
   - 确认或要求修改后立即通知最新批次状态。
   - 进度签名加入 `review_status`，避免审核状态变化被去重。
4. `app/ui/panels/tasks.py`、`app/ui/state.py`
   - 新增“待写入草稿”收件箱、筛选、标签、颜色和下一步动作。
   - 新增 `task_center_workflow_stage()`，让步骤条根据有效批次状态动态切换。
5. `app/feishu/progress.py`、`app/feishu/presenter.py`
   - 已确认文章显示“等待写入草稿箱”，不再提示等待审核。

### 状态契约

```text
ready_for_review + review_status != confirmed  -> ready_for_review
ready_for_review + review_status == confirmed  -> ready_for_draft
ready_for_draft 开始写入                       -> injecting
全部 drafted / published                       -> drafted
confirmed 改回 needs_changes                   -> ready_for_review
存在 failed 且与其他终态混合                  -> partial_failed
```

### 验收结论

- “已审核 1/1、失败 0、已写入 0”返回 `ready_for_draft`：**通过**。
- 确认后“待审核”减 1、“待写入”加 1：**通过**。
- 收件箱、批次卡和飞书通知统一显示“待写入草稿”：**通过**。
- 改回“需要修改”后恢复“待审核”：**通过**。
- 任务中心步骤条进入“写入草稿”：**通过**。
  - `ready_for_draft`、`injecting`、`drafted`、`published` 映射为 `draft`。
  - 仍有未确认文章时保持 `review`。
  - `partial_failed + unconfirmed>0` 保持审核；无未确认且存在待写入或已写入文章时进入草稿阶段。
- 页面不再同时保留固定审核步骤条和动态步骤条：**通过**。

### 研发复核发现与关闭记录

首次正式复核时，开发大总管发现任务中心顶部仍固定调用审核步骤条，因此将该项判为“部分通过”。随后完成以下补正：

2. 增加单一可刷新 `workflow_host`。
3. 完成态与“待写入草稿”收件箱使用动态阶段映射。
4. 增加 `ready_for_review`、`ready_for_draft`、`injecting`、`drafted` 和两类 `partial_failed` 测试。

开发大总管复核补正代码并独立运行相关测试后，确认该缺口已关闭。

## 四、P0-2：生成完成后聚焦本次任务

### 研发判断

旧流程虽然会切换到任务中心，但只保存 `focus_batch_id` 并滚动到目标卡片，历史计数和历史文章仍先被渲染。任务中心采用懒挂载，首次生成时还存在刷新入口尚未创建、完成事件丢失的风险。

### 开发任务与实现证据

1. `app/ui/state.py` 增加一次性 `pending_task_center_entry`，切换用户时清空。
2. `app/ui/desktop.py` 在生成完成时使用 `entry_mode='completion'`；任务中心尚未挂载时保存一次性入口，挂载后消费并清空。
3. `app/ui/panels/tasks.py`
   - 增加 `completion_batch_id` 完成态。
   - 只读取并展示本批次摘要，不查询或渲染历史文章。
   - 主 CTA 为“审核第 1 篇”，复用现有审核工作台。
   - 提供“返回待处理收件箱”。
   - 最后一篇确认后重新读取批次，继续停留在本批次并显示写入 CTA。
4. 主动进入后台的生成任务继续使用 `activity` 模式，不会误显示完成页。

### 验收结论

- 生成完成自动进入本次任务摘要：**通过**。
- 完成态首屏不渲染其他历史文章：**通过**。
- 单公众号一次点击进入第一篇审核：**通过**。
- 多公众号继续使用 `next_review_job()` 逐篇处理：**通过现有状态流**。
- 最后一篇确认后停留在本批次并显示写入 CTA：**通过**。
- 返回普通收件箱：**通过**。
- 从未打开任务中心时不丢失完成入口：**通过**。
- 1280×720 真实首屏视觉效果：**通过浏览器人工复验**；完成态首屏仅显示本次批次、首篇审核 CTA 和返回收件箱入口。

## 五、P0-3：配置检查分项反馈

### 研发判断

旧欢迎页将自动检查作为一次后台调用，只显示统一 loading；服务端没有中间事件通道，页面只能在全部完成后一次性展示结果。

### 开发任务与实现证据

1. `app/services/onboarding.py`
   - 定义六项稳定检查键：`article_ai`、`account`、`connection`、`draft`、`material`、`creation_plan`。
   - `status()` 和 `auto_check()` 增加 `on_progress`，发送经过脱敏的 `running/passed/failed` 事件。
   - UI 回调异常不会中止真实检查。
2. `app/ui/panels/onboarding_wizard.py`
   - 欢迎页预建六行检查结果，点击后立即显示。
   - 使用线程安全队列传递增量事件，UI 每 100ms 更新。
   - 10 秒显示“仍在检查”；30 秒只标记尚未完成的项目。
   - 失败项显示“重试本项”和“去修复”。
   - `_run_single_check()` 只更新用户选择的可见项目。
   - 最终使用权威 `status/account_checks` 再投影结果，避免过程事件成为第二套业务状态源。
3. 修复入口映射：
   - 文章 AI → AI 配置。
   - 公众号、创作方案 → 公众号配置。
   - 连接、草稿、素材 → 微信连接检查。

### 验收结论

- 点击后出现六项列表：**通过浏览器实测**；点击后约 412ms 出现完整六项列表。
- 六项支持等待中、检查中、通过、失败和超时：**通过**。
- 10 秒等待提示、30 秒单项超时标记：**通过**。
- 失败不清空已通过结果：**通过**。
- 失败项原位重试：**通过**。
- 失败项进入对应修复步骤：**通过**。
- 进度事件不包含 API Key 或 Authorization：**通过自动化测试**。

### 真实边界

- 30 秒是 UI 超时标记，不会强制取消底层请求；最终结果返回后会覆盖超时标记。
- `creation_plan` 当前由 `content_ready` 推断，不是对每个创作方案记录的独立远程检查。
- 连接、草稿、素材底层仍由一次 `preflight_accounts()` 完成，不是三个独立网络请求。
- 六项增量体验目前位于首次欢迎页“我已经配置过，自动检查”路径；设置页未同步增加同一组件。
